Act as a **Principal Software Architect, Senior Full-Stack Engineer, Technical Documentation Architect, Knowledge-Graph Engineer, UX/UI Designer, and Engineering Education Specialist**.

# 2. Project identity

**Project name:** My End-to-End Tech & Engineering Codex

**Project type:** Personal Engineering Encyclopedia, Knowledge Graph, Learning Management System, Career Roadmap, Technical Reference Library, and Engineering Inventory.

### Main vision

I want one centralized website where I can learn, explore, connect, organize, and track practically every major area of technology and engineering.

The website should feel like a combination of:

- Wikipedia — interconnected encyclopedia articles and references.
- GeeksforGeeks — structured technical explanations, examples, tutorials, and learning paths.
- MDN Web Docs — reliable technical documentation and detailed explanations.
- Roadmap.sh — visual career and technology roadmaps.
- Obsidian/Logseq — interconnected knowledge and backlinks.
- GitBook — organized technical documentation.
- Personal learning management system — progress tracking and personal notes.

These are design and information-architecture inspirations, not websites to copy.

I do NOT want a basic dashboard containing a few cards for Software Development, AI, Cloud, IoT, Cybersecurity, etc.

I want a real knowledge system in which every important concept is an individually explorable entity connected to other relevant concepts.

**The fundamental principle: Everything should connect to everything it is technically or conceptually related to, without creating meaningless relationships.**

# 4. Most important instruction: Use research.md as the primary knowledge source

I have created a file named:

`research.md`

It contains my research, questions, explanations, technical concepts, comparisons, learning discussions, career-related research, and other material gathered from previous learning sessions.

**You MUST read the complete `research.md` before designing the knowledge architecture or migrating its content.**

Do not read only its beginning or search for a few keywords and ignore the remaining content.

Treat it as the initial knowledge corpus for the project.

### How to process research.md

For every meaningful topic:

1. Identify the actual concept being discussed.
2. Extract its definition and explanation.
3. Identify its technical category.
4. Identify prerequisites.
5. Identify related concepts.
6. Identify related technologies, tools, and protocols.
7. Identify related engineering roles.
8. Identify examples and practical applications.
9. Identify any security implications.
10. Identify questions that need further research.
11. Preserve useful explanations and comparisons.
12. Organize it into individual knowledge articles.

- JavaScript execution model

- CPU cores
- Scheduling

Create relationships between these concepts so that exploring one naturally leads to the others.

Apply this extraction process to the entire research file.

### Research preservation

Do not silently discard material just because it does not fit the initial taxonomy.

If a topic is incomplete, uncertain, outdated, duplicated, or requires verification:

- Preserve the original material.
- Mark its verification status.

# 11. Standardized technical article quality

I am confused by the fact that different websites explain the same concept differently.

I want the Codex to establish a consistent documentation standard.

For every technical article, follow this structure:

## 1. Definition

Provide a precise, technically correct definition.

## 2. Simple explanation

Explain it in beginner-friendly language.

## 3. Why it exists

Explain the problem it was created to solve.

## 4. How it works

Explain the internal mechanism step by step.

## 5. Architecture and components

Explain the parts and how they interact.

## 6. Technical terminology

Define important terms.

## 7. Practical example

Give a realistic example.

## 8. Code or implementation

Where applicable, show code, commands, configuration, or pseudocode.

## 9. Diagram

Show the architecture, workflow, lifecycle, or communication process.

## 10. Applications

Explain where it is used in real systems.

## 11. Advantages and limitations

Explain trade-offs and boundaries.

## 12. Security and reliability

Explain relevant risks and defensive considerations.

## 13. Common problems

Include errors, misconceptions, and troubleshooting.

## 14. Related concepts

Link to relevant Codex articles.

## 15. Learning progression

Explain prerequisites and the next concepts to study.

## 16. Engineering roles

Explain which professional roles use this knowledge.

## 17. References

Provide trustworthy resources and sources.

Do not force irrelevant sections into every article. For example, a mathematical concept does not need a hardware security section.

### Definition consistency

When a concept has multiple accepted meanings:

- Explain the context.
- Distinguish different uses.
- Mention important terminology differences.
- Identify the standards or implementations that define its behavior.
- Avoid presenting one vendor's definition as universal.

Where relevant, distinguish:

- Concept vs implementation.
- Specification vs product.
- Protocol vs application.
- Programming language vs runtime.
- Framework vs library.
- Tool vs technology.
- Job title vs professional specialization.

# 12. Research quality and source management

The Codex must not become a collection of unverified AI-generated definitions.

Build a source and verification system.

Prioritize sources in this order where appropriate:

1. Official standards and specifications.
2. Official product documentation.
3. Official language and framework documentation.
4. Government and recognized technical institutions.
5. Peer-reviewed research papers.
6. Reputable technical textbooks.
7. Well-established educational references.
8. Community explanations and discussions.

Examples include:

- IEEE standards.
- RFC documents.
- W3C.
- WHATWG.
- ISO/IEC.
- NIST.
- OWASP.
- MDN.
- Linux documentation.
- Microsoft Learn.
- AWS documentation.
- Google Cloud documentation.
- Official GitHub repositories.
- Official hardware manufacturer documentation.

Each article should support:

- Source title.
- Publisher.
- URL.
- Source type.
- Date accessed or verified.
- Relevant claims supported by the source.
- Current verification status.

Use a verification status such as:

- Verified
- Needs review
- Outdated
- Conflicting sources
- Incomplete
- Personal notes

For fast-changing areas such as AI, cloud platforms, cybersecurity, and software frameworks, display a last-verified date.

Never invent citations, specifications, versions, or official standards.

When sources disagree, explain the disagreement instead of silently choosing one.
