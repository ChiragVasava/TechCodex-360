
how dom and cssom work together

The DOM and CSSOM combine to form the Render Tree, which the browser uses to calculate element sizes and paint pixels onto the screen.
While both models are built independently during page load, they work together in a step-by-step pipeline known as the Critical Rendering Path:

1. Parallel Tree Construction

• DOM (Content and structure). As the browser parses HTML, it converts tags into nodes and links them into a tree representing the page's hierarchy. This process is incremental—the browser can start building the DOM before the entire HTML file finishes downloading.
• CSSOM (Styles and rules). Simultaneously, the browser parses all CSS (inline, internal, external, and default browser styles) to build a separate style tree. Because CSS rules cascade and later rules can override earlier ones, the browser must wait for all CSS to download and parse before moving forward.

2. Merging into the Render Tree

Once both trees are ready, the browser traverses the DOM starting from the root and matches each visible node with its corresponding style rules from the CSSOM.
The resulting Render Tree includes only the elements that will actually appear on the screen:
• Excluded elements. Non-visual tags (like <head>, <meta>, and <script>) and elements hidden with display: none are left out entirely.
• Included elements. Elements with visibility: hidden or opacity: 0 remain in the Render Tree because they still take up physical space on the page.

3. Layout and Paint

• Layout (Reflow). Using the Render Tree, the browser calculates the exact geometry—width, height, and screen coordinates—for every visible node based on viewport size and CSS box-model rules.
• Paint (Rasterization). Finally, the browser translates those calculated boxes and visual styles (colors, borders, text, shadows) into actual pixels on the screen.

Dynamic Updates via JavaScript

Because both trees remain live in memory, JavaScript can modify either one at any time using Web APIs (such as document.querySelector() for the DOM or element.style for the CSSOM). Whenever a script alters a node or style rule, the browser automatically updates the affected tree, rebuilds the relevant portion of the Render Tree, and re-runs Layout and Paint.

What is Shadow DOM Concept Where it is use for what ?

Shadow DOM is a browser feature that lets you attach a hidden, isolated DOM tree to a regular HTML element, keeping its internal structure and CSS styles completely separate from the rest of the page.
Think of it as a protective bubble around a specific piece of UI. Code outside the bubble cannot accidentally break what is inside, and styles inside won't leak out to mess up the rest of your website.

How it solves common web problems

On a normal webpage, all HTML and CSS share one global space. If you load a third-party widget or build a complex component, a generic CSS rule like button { background: red; } on your main page can accidentally restyle buttons inside that widget. Shadow DOM prevents these collisions through encapsulation:
• Style isolation: CSS written inside a Shadow DOM applies only to elements inside that shadow tree. Page-level CSS rules cannot bleed in (except for inherited properties like color or font-family).
• DOM isolation: Standard selection methods like document.querySelector() on the main page cannot reach inside a Shadow DOM.

Where and why it is used

• Built-in browser controls: Browsers actually use Shadow DOM behind the scenes for native tags like <video>, <audio>, and <input type="range">. When you put a <video> tag on a page, the play button, timeline slider, and volume icon live inside a hidden Shadow DOM that the browser manages for you.
• Web Components: Developers use it alongside Custom Elements to build reusable UI components (like custom date pickers, modals, or design system buttons) that look and behave identically no matter what website they are dropped into.
• Third-party embeds and widgets: Chat widgets, payment forms, and social media embeds use Shadow DOM so that a host website's stylesheet doesn't break their layout or branding.
• Browser extensions: Extensions inject UI panels onto existing websites using Shadow DOM so the website's CSS doesn't distort the extension's interface.

Basic code example

You create a Shadow DOM in JavaScript by calling .attachShadow() on a host element:
javascript
// 1. Select a normal element to act as the "Shadow Host"
const host = document.querySelector("#my-widget");

// 2. Attach a Shadow Root to it
const shadow = host.attachShadow({ mode: "open" });

// 3. Add isolated HTML and CSS inside the Shadow DOM
shadow.innerHTML = `
  <style>
    p { color: blue; font-weight: bold; } /* Only affects <p> inside this shadow tree */
  </style>
  <p>I am safely inside the Shadow DOM!</p>
`;
Use code with caution.
(Note: mode: "open" allows your JavaScript to access the shadow tree later via host.shadowRoot, while mode: "closed" locks it away from external scripts completely.)

Here is how they actually exist in both places:

1. In a normal webpage

A standard webpage runs on the Regular DOM (also called the Light DOM), which holds all your normal HTML tags (<div>, <p>, <header>). Custom Elements, Shadow DOM, and HTML Templates are the three core technologies that make up Web Components, allowing you to create reusable, self-contained HTML elements with standard browser APIs.
Each one has a distinct job, and together they let you build custom UI pieces (like a <star-rating> or <user-card>) that work across any framework or plain HTML.

1. Custom Elements

Custom Elements let you define your own HTML tags and control how they behave using JavaScript classes.
• Purpose: Extend HTML with semantic, reusable tags instead of nesting dozens of generic <div> tags.
• Use: You register a new tag name (which must include a hyphen, like <alert-box>) using customElements.define(), and define lifecycle hooks (like connectedCallback() when added to the page or attributeChangedCallback() when an attribute changes).

2. Shadow DOM

Shadow DOM attaches an isolated, hidden DOM and style scope to an element.
• Purpose: Encapsulate markup and CSS so styles don't leak out and page styles don't accidentally break the component.
• Use: Call element.attachShadow({ mode: "open" }) to keep a component's internal structure and <style> rules self-contained. (Note: Avoid repeating what was already covered in detail earlier—keep it focused on its role alongside Custom Elements and Templates.)

3. HTML Templates (<template> and <slot>)

HTML Templates let you declare inert chunks of markup in HTML that the browser parses but does not render immediately until cloned via JavaScript.
• Purpose: Define clean, reusable blueprints directly in HTML without writing long HTML strings inside JavaScript or showing unused content on initial load.
• Use: Wrap markup in <template id="card-tpl">, clone it in JavaScript using tpl.content.cloneNode(true), and inject it into a Custom Element or Shadow DOM. You can also use <slot> tags inside a Shadow DOM to let users pass custom content into specific spots of your component.

How They Work Together

1. HTML Template defines the blueprint (and optional <slot> placeholders) in your HTML.
2. Custom Element registers the new tag name and manages its JavaScript logic and attributes.
3. Shadow DOM isolates the cloned template's HTML and CSS inside that custom element.

What are these ? what is their use & purpose ?

Cookies, Local Storage, Session Storage, and IndexedDB are browser storage mechanisms used to save data on the user's device across requests, page reloads, or browsing sessions.
Each one stores data differently, with trade-offs in capacity, lifespan, and whether it gets sent to the server.

1. Cookies

Small text key-value pairs stored by the browser and automatically attached to HTTP requests sent to the matching domain.
• Purpose: Maintain server-aware state (such as session identifiers) and support authentication or tracking across page loads.
• Use & Limits: Typically capped around 4 KB per cookie and expire on a set date/time (or when the browser closes if no expiration is set). Because they travel with HTTP requests, keeping them small avoids slowing down network traffic.

2. Local Storage

A simple synchronous key-value store tied to an origin (window.localStorage) that persists even after closing the browser or restarting the device.
• Purpose: Keep non-sensitive preferences or cached state available across visits without sending it on every network request.
• Use & Limits: Stores strings (use JSON.stringify() and JSON.parse() for objects/arrays), typically offering around 5–10 MB per origin. Data remains until explicitly cleared by code, the user, or browser storage cleanup.

3. Session Storage

A key-value store (window.sessionStorage) with a similar API to Local Storage, scoped to a single browser tab for the lifetime of that tab.
• Purpose: Hold temporary state tied to one active workflow or tab without leaking into other tabs or surviving after the tab closes.
• Use & Limits: Also stores string key-value pairs (around 5 MB), cleared immediately when the tab or window closes. Reloading the same tab preserves it, whereas opening a new tab starts fresh.

4. IndexedDB

A low-level, asynchronous client-side database (often object-store based with indexes) built into the browser for structured data and larger volumes.
• Purpose: Store large amounts of structured data, binary blobs/files, or rich app state for fast querying and offline-capable web apps.
• Use & Limits: Handles much larger quotas than localStorage (dynamic/disk-dependent per browser and origin) without blocking the main UI thread like synchronous storage calls can. Often wrapped with a helper library (such as idb or Dexie) for cleaner async/await ergonomics.

Best fit	Auth/session IDs, server hints	UI themes, saved settings	Multi-step tab forms, temp state	Offline data, large JSON/files

The website you visit must explicitly create and write this data—the browser simply provides the storage spaces and enforces their rules, rather than saving page data on its own.
Think of the browser like a set of locked storage lockers on your device, and the website (or its server) holds the keys to put things inside:

1. Local Storage, Session Storage, and IndexedDB

• 100% website-driven. The browser never populates these automatically.
• A website must run JavaScript code (such as localStorage.setItem("theme", "dark")) to store anything in them. If a webpage doesn't run storage scripts, these remain completely empty.

2. Cookies

• Created by the website's server or JavaScript, though the browser automatically sends them back once they exist.
• A website creates a cookie in one of two ways:
	• Server-side: The website's server sends a Set-Cookie HTTP header in its response when you load a page or log in, instructing your browser to save it.
	• Client-side: The website's JavaScript runs document.cookie = "...".
• Once the website puts a cookie into your browser, the browser automatically attaches that cookie to future requests you make to that same website until it expires.

What the Browser Does Store Automatically

While the browser won't create Cookies, Local Storage, Session Storage, or IndexedDB entries on its own, it does automatically manage its own internal features—such as HTTP Cache (saving images, CSS, and scripts so pages load faster next time), browsing history, and autofill/saved passwords (if you allow it).

Correct—autofill data and saved passwords are never stored in Cookies, Local Storage, Session Storage, or IndexedDB.
They are stored in a separate, encrypted internal database managed directly by your browser (often tied to your operating system's security keychain or your browser profile), completely isolated from websites.

Why browsers keep them separate

• Website access: Any JavaScript running on a webpage can freely read its own localStorage, sessionStorage, IndexedDB, and non-HttpOnly cookies. If passwords lived there, malicious scripts or cross-site scripting (XSS) attacks could easily steal them.
• Encryption & OS protection: Your browser encrypts saved passwords using operating-system-level security (like Windows Credential Manager, macOS Keychain, or Android Keystore) and only fills them into a form when you interact with the page or unlock your profile.
• Websites cannot read them directly: Even when your browser autofills a password field, the website only receives the password once you submit the form or trigger input events—it cannot query your browser's password vault on its own.

What is stored in Cookies/Storage during login?

When you log into a site, the website doesn't save your actual password in Cookies or Local Storage. Instead, the server checks your password, generates a temporary session ID or authentication token, and saves that token in a Cookie (ideally an HttpOnly cookie so JavaScript cannot touch it) to keep you logged in.

Each storage mechanism has its own specific API calls, so you cannot just call a single built-in browser function for all four—though you can write your own wrapper function in JavaScript that routes data to whichever mechanism you choose based on what you pass to it.

1. What you call for each mechanism

• Cookies: Write via document.cookie = "key=value; path=/; max-age=3600" in JavaScript (or via the server's Set-Cookie header).
• Local Storage: Call localStorage.setItem("key", "value") (and JSON.stringify() if saving an object).
• Session Storage: Call sessionStorage.setItem("key", "value").
• IndexedDB: Open a database with indexedDB.open("dbName", version), start a transaction, get an object store, and call .put() or .add() (which is event-based and asynchronous).

2. Using a single custom wrapper function

Because Local Storage and Session Storage share the exact same method names (setItem / getItem), it is easy to write one custom helper function that picks the right storage for you:
javascript
function saveData(storageType, key, value) {
  if (storageType === "local") {
    localStorage.setItem(key, JSON.stringify(value));
  } else if (storageType === "session") {
    sessionStorage.setItem(key, JSON.stringify(value));
  } else if (storageType === "cookie") {
    document.cookie = `${encodeURIComponent(key)}=${encodeURIComponent(JSON.stringify(value))}; path=/`;
  } else if (storageType === "indexeddb") {
    // Requires opening DB + transaction + objectStore.put()
  }
}

Why you usually don't force everything into one function

Even with a wrapper, IndexedDB works asynchronously (using requests/events or Promises) while Cookies, Local Storage, and Session Storage are synchronous, and Cookies also have attributes like HttpOnly, SameSite, and expiration dates. In practice, developers usually separate storage helpers by purpose (for example, a small helper for preferences in localStorage and a dedicated async module for larger offline data in IndexedDB).
